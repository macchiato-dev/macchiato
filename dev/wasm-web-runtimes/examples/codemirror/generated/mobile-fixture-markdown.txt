# AGENTS.md

## Runtime

Prefer Deno for new JavaScript and TypeScript tooling, build scripts, and
services. Do not introduce Node-only dependencies or npm-driven tooling when a
straightforward Deno implementation is available.

Some existing packages still use Node APIs such as `node:sqlite`. Treat Node as
a compatibility runtime for those packages while they are being migrated, not
as the repository's preferred runtime. When touching one, use a current Node
release and avoid expanding its Node-specific surface.

Check the preferred runtime with:

```bash
deno --version
```

When an existing Node-only package must be run, also check `node -v` first.

## Containers

Use Fedora-based images for development and build containers. Podman is the
primary container engine. Containerfiles must work with Podman and use the
Docker-compatible subset needed for GitHub Actions, where Docker is the
explicit compatibility exception. Do not introduce Debian- or Ubuntu-specific
package management unless a narrowly scoped upstream build requires it and the
exception is documented.

Keep the Bunny deployment container separate and deliberately narrow. Its
reason to exist is to receive the Bunny API key temporarily and perform the
deployment. It should contain only the deployment client and the minimum
artifacts and instructions needed for that operation. Building, packaging,
serving, development authentication, and unrelated tooling stay outside this
key-bearing container and must not receive the key.

Do not depend on base images or build images available only from Docker Hub.
Prefer fully qualified OCI image references from Fedora's registries, GHCR, or
another registry that works directly and predictably with Podman. Docker Hub
may be an additional mirror, but it must not be the sole source.

## JavaScript Modules and Working Files

Use JavaScript modules throughout this repository. Use the `.js` extension,
not `.mjs`; place standalone scripts beneath a directory whose `package.json`
sets `"type": "module"`.

Avoid using `/tmp` for working files and reusable diagnostics. Prefer a clearly
named sibling directory beside the repository, such as `/root/macchiato-work`,
with its own `package.json` when it contains standalone module scripts.

## Development History

Commit at useful, coherent checkpoints often enough that meaningful
work-in-progress remains visible. There is no need to commit every tiny edit.
Experimental commits are welcome: it is fine to backtrack when an approach does
not work, and seeing that evolution is useful when reviewing the project.
If substantial work has accumulated without a checkpoint, commit a coherent
portion with `WIP` in the message even when it is not fully verified. Follow it
with a correcting or completing commit after testing rather than hiding the
intermediate state in a long-running worktree.

## Running the Server

For local development, pick a port that is free on your machine. The examples
below use `8765`, which is the app package default and is usually available for
local self-hosting.

```bash
cd /path/to/macchiato
node packages/app/src/index.js --host 127.0.0.1 --port 8765
```

A fresh database initializes only the `core` app-directory preset. For the full
repository demo set, use `--app-plugin development`. See
`docs/declarative-apps.md` for persistent installation and subdomain mapping.

If running inside a container or VM and exposing the port to the host, bind to
all interfaces inside the container:

```bash
node packages/app/src/index.js --host 0.0.0.0 --port 8765
```

Useful local URLs after installing the relevant apps:

```text
http://macchiato.localhost:8765
http://dom-use.localhost:8765
http://dom-use-todos.localhost:8765
http://todo.localhost:8765
```

## Site Configuration

List configured SQLite-backed sites with:

```bash
node packages/macchiato/src/macchiato.js site list
```

Use `--data-dir <dir>` before the command when you want an explicit SQLite
directory, for example:

```bash
node packages/macchiato/src/macchiato.js --data-dir ./macchiato-dev-data site list
node packages/app/src/index.js --data-dir ./macchiato-dev-data --host 127.0.0.1 --port 8765
```

Add a site with:

```bash
node packages/macchiato/src/macchiato.js schema add \
  @macchiato-dev/dom-use@0.0.1/article.json \
  examples/dom-use-demo/dom.schema.json

node packages/macchiato/src/macchiato.js schema add \
  @macchiato-dev/style-use@0.0.1/basic.json \
  examples/dom-use-demo/css.schema.json

node packages/macchiato/src/macchiato.js site add-page \
  dom-use \
  examples/dom-use-demo/page.html \
  examples/dom-use-demo/style.css \
  @macchiato-dev/dom-use@0.0.1/article.json \
  @macchiato-dev/style-use@0.0.1/basic.json \
  --title "Neighborhood Library"
```

The app server routes by subdomain, so a `dom-use` row is served at
`http://dom-use.localhost:<port>`.

## Copying Container Files to the macOS Clipboard

The repository normally runs in the `macchiato-vibe` Podman container inside
Lima, while `pbcopy` belongs to the macOS host. To copy a generated or source
file out of the container, stream it through `podman exec` and pipe it to the
host clipboard. In an environment that uses `!` for host shell commands, copy
the Bunny nested-worker probe with:

```bash
!lima podman exec macchiato-vibe cat /root/macchiato/examples/bunny-edge-worker-probe/worker-probe.js | pbcopy
```

Use the same form for other files, changing only the absolute container path.
Do not run `pbcopy` inside the container.

# macchiato

A self-hosted app platform.

## Components

Macchiato is split into small packages with explicit boundaries. The runtime
server composes them, but the policy and validation pieces are reusable on
their own.

| Component | Description |
|-----------|-------------|
| [`@macchiato-dev/app`](packages/app/) | Cross-runtime HTTP server. Routes only declaratively registered apps by subdomain and serves their handlers or SQLite-backed content. |
| [`@macchiato-dev/macchiato`](packages/macchiato/) | CLI and interactive shell for managing the local Macchiato database: sites, schemas, routes, fonts, and server lifecycle helpers. |
| [`@macchiato-dev/app-db-sqlite`](packages/app-db-sqlite/) | SQLite storage layer for app configuration. Owns schema creation, migrations, query helpers, and prepared-statement-backed access for the app database without becoming a full ORM. |
| [`@macchiato-dev/site`](packages/site/) | SSR site framework for full HTML documents, route rows, transition policy, trusted pre-sanitized page swaps, and fallback navigation. |
| [`@macchiato-dev/dom-use`](packages/dom-use/) | Top-level schema-bound DOM capability. Guest code creates and mutates DOM through this package, which enforces allowed nodes, attributes, parent/child relationships, URL rules, content limits, and DOM gas budgets. |
| [`@macchiato-dev/html-use`](packages/html-use/) | Lower-level HTML parser, serializer, and sanitizer used by `dom-use`. It receives the caller's element factory and schema instead of importing `dom-use` directly. |
| [`@macchiato-dev/style-use`](packages/style-use/) | CSS policy engine for inline styles and stylesheets. Schemas declare allowed properties, value patterns, selectors, at-rules, URL loading, imports, and stylesheet limits. |
| [`@macchiato-dev/theme-use`](packages/theme-use/) | Validates named, allowlisted CSS custom-property themes and renders customizable theme declarations without permitting active CSS values. |
| [`@macchiato-dev/menu-use`](packages/menu-use/) | Defines one immutable primary-navigation model and renders matching desktop, mobile, and document-runtime menus. |
| [`@macchiato-dev/user-menu-use`](packages/user-menu-use/) | Compiles declarative user-menu definitions into markup, colocated `dom-use` schema capability, and an exclusive open/close state machine suitable for a sandbox. |
| [`@macchiato-dev/font-use`](packages/font-use/) | Font asset cache helpers. Validates font names and paths, stores known font bytes in SQLite, emits stable `/-/fonts/...` URLs, and builds `@font-face` declarations. |
| [`@macchiato-dev/quickjs-emscripten-sandbox`](packages/quickjs-emscripten-sandbox/) | QuickJS-backed JavaScript sandbox. Runs guest JavaScript with explicit host capabilities and provides browser assets used by the DOM sandbox examples. |
| [`@macchiato-dev/dashboard`](packages/dashboard/) | Small management UI for local site mappings. It is a development convenience, not the core storage or policy layer. |

The core capability stack is:

```text
dom-use
  |-- html-use
  `-- style-use
```

`dom-use` is what guest contexts interact with. `html-use` and `style-use` are
implementation capabilities that can also be used directly where lower-level
HTML or CSS validation is needed.

## Examples

App installation, dependency mapping, and the minimal default are described in
[Declarative apps](docs/declarative-apps.md).

| Example | Description |
|---------|-------------|
| `examples/dom-use-demo` | SQLite-backed page example. Imports an HTML fragment, stylesheet, DOM schema, and CSS schema into the app database and serves the result at `dom-use.localhost`. |
| `examples/dom-use-todos` | QuickJS-backed todo app. Passes `examples/todo/index.html` into the guest runtime and applies `dom-use` validation to every guest DOM operation. |
| `packages/website` | Private `@macchiato-dev/website` workspace containing the Resources.co content, skin, publication build, and Bunny Edge deployment entrypoint. |
| `examples/resources-website` | Multi-page Resources.co website example used for schema-bound page, style, navigation, prefetch, and transition work. |
| `examples/todo` | Standalone prototype of a guest-side DOM simulation with host-side rendering. |
| `examples/todo-matrix` | QuickJS/schema-constrained todo matrix app with local storage and grid interaction. |

## Dependency Policy

Packages in this monorepo specify **exact versions** for all dependencies.
Nested dependencies may technically be pulled in by npm during installation,
but the project does not serve files from nested `node_modules` packages.
Each package is responsible for its own runtime surface and should not
expose its transitive dependency tree over the network.

This policy is pragmatic, not dogmatic — exceptions may exist where
strict exact-version pinning would create unnecessary friction.

The proposed npm release groups, dependency order, and release gates are in
[docs/npm-publishing.md](docs/npm-publishing.md). Public publishing is blocked
until the repository has an explicit license.

## Running with Deno

`deno install` grants permissions — it cannot preset environment variables.
Use CLI flags or the SQLite database for runtime configuration.

### Install the server directly (tightest permissions)

Best for running just the HTTP server without the interactive shell:

```bash
deno install \
  --allow-net=[::]:3030 \
  --allow-read=$HOME/.macchiato/default \
  --allow-write=$HOME/.macchiato/default \
  --allow-env=HOME,USERPROFILE \
  ./packages/app/src/index.js
```

Then run it on port 3030:

```bash
macchiato-app --port 3030
```

### Install the full CLI (includes interactive shell)

The `macchiato` CLI can start and stop the server from an interactive shell.
In Deno this requires `--allow-run` to spawn the server process:

```bash
deno install \
  --allow-net=[::]:3030 \
  --allow-read=$HOME/.macchiato/default \
  --allow-write=$HOME/.macchiato/default \
  --allow-env=HOME,USERPROFILE \
  --allow-run=deno \
  ./packages/macchiato/src/macchiato.js
```

Then:

```bash
macchiato                          # enter interactive shell
macchiato> server start --port 3030
macchiato> site add todo ../../examples/todo
```

The `examples/dom-use-todos` example passes `examples/todo/index.html`

Then open:

### Permission notes

| Flag | What it allows |
|------|---------------|
| `--allow-net=[::]:3030` | Bind the server to port 3030 on all interfaces (IPv6 dual-stack) |
| `--allow-read=$HOME/.macchiato/default` | Read the SQLite database |
| `--allow-write=$HOME/.macchiato/default` | Write the SQLite database (WAL creates `-wal` and `-shm` siblings) |
| `--allow-env=HOME,USERPROFILE` | Resolve the `~/.macchiato/default` data directory |
| `--allow-run=deno` | *(CLI only)* Spawn the server as a subprocess |

If you only need localhost (not `0.0.0.0`), replace `[::]:3030` with `127.0.0.1:3030`.

# Macchiato EVM

An allocator-free `no_std` Ethereum Virtual Machine designed to run directly
in WebAssembly and to remain understandable enough to inspect opcode by
opcode.

The implementation is under active construction. It currently targets Cancun
execution semantics for its implemented opcode set. Unsupported opcodes stop
with an explicit status; they are never silently approximated.

## Design

- The core has no allocator, libc, WASI, filesystem, clock, network, or random
  source.
- Callers provide code, calldata, environment values, gas, and persistent
  storage. The machine uses caller-owned bounded stack, memory, transient
  storage, logs, output, and trace buffers. `Workspace` is the browser's
  64 KiB profile; `WorkspaceWithCapacity<N>` selects a larger allocation-free
  profile when execution needs it.
- The optional `Host` trait supplies account balances and code, block hashes,
  and blob hashes. It reports cold account accesses, leaving state layout and
  database choice outside the VM while keeping EIP-2929 gas in the core.
- A word is four little-endian `u64` limbs. Arithmetic wraps modulo `2^256`.
- The Wasm ABI uses exported linear-memory buffers and integer lengths. JSON is
  a playground concern and does not cross the VM boundary.
- Every executed instruction may produce a compact trace record containing the
  program counter, opcode, remaining gas, stack height, and stack top.

Ethereum's executable execution-layer specification is the semantic reference:
<https://github.com/ethereum/execution-specs>. Tests should prefer official
execution-spec vectors as coverage expands.

The checked-in compact corpus currently runs 325 Cancun cases derived from
`execution-spec-tests` v5.4.0: arithmetic and bitwise operations, direct
calldata loads, `MCOPY`, memory and control flow, Keccak, and return data. Each
corpus records its source or aggregate SHA-256. Three EIP-1153 cases execute
recursive `CALL`, `CALLCODE`, and `DELEGATECALL` frames through a test host and
check their distinct transient-storage ownership. Cases that intentionally
need more than the browser ABI's default 64 KiB memory bound run in explicitly
larger caller-selected profiles.

## Layout

- `src/word.rs` — dependency-free 256-bit integer operations.
- `src/machine.rs` — execution state, gas, memory, storage, and opcodes.
- `src/wasm.rs` — a compact browser-facing ABI.
- `playground/` — static browser UI, examples, and Playwright tests.

The current standalone frame implements arithmetic, comparison and bitwise
instructions; Keccak-256; calldata, code and return-data access; bounded
memory; persistent and transient storage; control flow; logs; Cancun's
`PUSH0`, `MCOPY`, `TLOAD`, and `TSTORE`; and the environment values exposed by
the playground. Storage changes and logs roll back on `REVERT` and exceptional
termination.

With a host, account and external-code inspection, block and blob hashes,
host-backed persistent and transaction-wide transient storage, calls, contract
creation, and post-Cancun self-destruction are available. Calls and creation
use typed requests plus bounded input and return buffers; a host may recursively
invoke `Machine` for child frames. Checkpoints make host mutations, including
transient writes, commit only on successful frame termination.
Precompiles and transaction-level refund capping belong to the host. The core
calculates frame-level Cancun `SSTORE` costs and refund deltas.

## Build

```sh
PATH="$HOME/.cargo/bin:$PATH" cargo test --manifest-path dev/evm/Cargo.toml
deno run --allow-env=PATH,HOME --allow-read=. \
  --allow-write=dev/evm/playground,dev/evm/target \
  --allow-run="$HOME/.cargo/bin/cargo" dev/evm/build.js
node --test dev/evm/test/*.test.js
```

The build copies a `wasm32-unknown-unknown` `cdylib` into
`playground/evm.wasm`. At this revision it is 42,122 bytes, imports nothing,
and has SHA-256
`abc91e307392d51b90985758b375b5fa805e2f79489f7e6c123765e7ef45da69`.
The browser test recompiles the module, checks that empty import list, checks
the ABI bounds, and executes every example.

`server.js` serves the playground on loopback. The development app plugin
declares `evm` as a proxy to that server, so the app gateway exposes the same
files at `http://evm.localhost:<port>` without an EVM-specific gateway handler.

## Browser ABI

Instantiate `playground/evm.wasm`, copy bytecode and calldata into the buffers
returned by `evm_code_ptr` and `evm_calldata_ptr`, and write fourteen 32-byte
big-endian environment words at `evm_environment_ptr`. Then set whether the
frame is static and run it:

```js
const { instance } = await WebAssembly.instantiateStreaming(fetch("./evm.wasm"));
const evm = instance.exports;
const memory = new Uint8Array(evm.memory.buffer);
memory.set(code, evm.evm_code_ptr());
memory.set(calldata, evm.evm_calldata_ptr());
evm.evm_set_read_only(0);
const exit = evm.evm_run(code.length, calldata.length, 1_000_000n, 100_000);
```

The stack, trace, and output each have pointer and length exports. The remaining
scalar results are `evm_gas_left` and the signed `evm_refund` counter.
`evm_reset_storage` clears the standalone playground's persistent storage.
Lengths exceeding the two 65,536-byte input capacities return `InputLimit`
without executing an instruction.

# MicroESNext

Design notes include the [ponyfill source survey](docs/ponyfill-sources.md) and
the implementation-independent [testing strategy](docs/testing.md).

MicroESNext is a new, single-crate experiment in progressively rewriting
MicroQuickJS in Rust. It starts from a compact C baseline rather than from the
earlier Rust-native object and memory model.

The baseline was copied without modification from a fresh checkout of
[`bellard/mquickjs`](https://github.com/bellard/mquickjs) at
`203d5bb79789bc47b74855d9207415dab71661a0`.

## Layout

- `src/` is the Rust crate. Rust replacements will enter here a bounded piece
  at a time.
- `c/` is the retained MicroQuickJS implementation. Its `generator/` subdirectory
  contains only the source generator needed to create the atom header.
- `docs/` contains source maps and design notes.

There is deliberately no `crates/` directory. A capability may become a Rust
module or Cargo feature, but it does not become a separate crate merely to
create an architectural boundary.

The C baseline includes the engine, bytecode definitions, UTF-8 and numeric
support, and soft-float templates. The build-only C helper generates the atom
header and is never linked into the library. The baseline excludes the `mqjs`
command-line shell, readline and terminal code, examples, executable test
programs, and the previous experiment's local `microesnext.c` companion.

`build.rs` uses the `cc` crate for both host and target C compilation. It builds
and runs the upstream ROM helper only long enough to generate
`mquickjs_atom.h`, then compiles the engine as a static library. It does not
compile the shell-owned default environment, whose generated table refers to
shell services such as printing, clocks, timers, and file loading. The crate
does not define or ship an executable.

The imported C sources retain their upstream copyright and license notices.
See [LICENSE](LICENSE).

# MicroQuickJS source outline

This is a qualitative map of the MicroQuickJS source set represented in
`dev/microquickjs-experiment/src`. It excludes locally added companion files,
such as `microesnext.c`, that are not MicroQuickJS source. The ranges are
one-based and inclusive. At each level they proceed from top to bottom without
gaps, so every included source line has a place in the outline. Filenames are
intentionally repeated to make sections convenient to copy, paste, and
rearrange.

The outline covers implementation files, headers, templates, the build file,
examples, and executable tests. It leaves out `LICENSE`, `Changelog`, and
`README.md`, which are legal or prose documents rather than program source.

# Ponyfill source survey

Source revisions inspected for the first Rust memory functions:

- wasi-libc `e1655e8857fc007512004414016e2dbf65bb8a21`
  - `libc-top-half/musl/src/string/memcmp.c`
  - `libc-top-half/musl/src/string/strlen.c`
- LLVM libc `533fa84a18f6bf722c3a756d4154a3dd1a4497bd`
  - `libc/src/string/memcmp.cpp`
  - `libc/src/string/strlen.cpp`
- Rust compiler-builtins `5c5f07851b1878013ac81e129b0517feaaf8661d`
  - `compiler-builtins/src/mem/mod.rs`
  - `compiler-builtins/src/mem/impls.rs`

wasi-libc uses a byte loop for scalar `memcmp` and an aligned word-at-a-time
`strlen`, with optional wasm SIMD paths. LLVM libc routes both through reusable
memory primitives intended for target specialization. Rust compiler-builtins
uses small pointer loops for these two operations and reserves word-wise paths
for copying and filling.

The initial Rust implementations follow compiler-builtins' pointer arithmetic,
copy direction, and byte loops. They preserve wasi-libc's exact `memcmp`
result: the unsigned-byte difference at the first mismatch. Rust
compiler-builtins adds aligned word paths above a small-copy threshold, while
wasi-libc adds optional wasm SIMD paths. The initial implementation stays
scalar and allocation-free; either optimization should be justified by wasm
measurements before it replaces the readable baseline.

MicroQuickJS's `js_malloc(ctx, size, mtag)` remains the engine allocator. It is
context-bound, tags every object, cooperates with collection and compaction,
and is not replaced by a general Rust global allocator.

# Incremental Rust rewrite order

This is a working order for replacing MicroQuickJS with Rust. The beginning is
specific enough to implement. Later phases are intentionally rough: findings
from the mixed C/Rust engine should determine their exact boundaries.

The rewrite keeps a runnable engine at every step. A replacement first matches
the C behavior suite, then becomes the implementation used by the mixed build.
Deleting the corresponding C comes last. Rust ownership is not imposed on C
memory before the surrounding lifetime rules are understood.

## Memory picture

MicroQuickJS receives one contiguous region. A context and heap grow upward
from its low address while the interpreter stack grows downward from its high
address. Heap blocks carry tags and sizes. JavaScript values contain immediate
data or pointers into that region. Explicit root records protect live values
across allocation, and garbage collection marks, sweeps, compacts, and rewrites
pointers. Compilation and bytecode relocation use the same physical model.

The rewrite should move through three memory arrangements:

1. **C-owned memory, Rust leaf functions.** Rust receives pointers and lengths,
   performs an operation, and neither retains nor allocates references. The C
   allocator, roots, collector, stack, and context remain authoritative.
2. **C-owned memory, Rust structure views.** Rust uses small unsafe types for
   tagged values, block headers, slices, and context fields. These are borrowed
   views into the existing region. Mutations still obey C allocation and root
   rules, and tests compare mixed-engine traces with the C baseline.
3. **Rust-owned arena and lifetimes.** Rust owns allocation metadata, roots,
   handles, collection, and compaction. JavaScript references should be typed
   handles or offsets rather than ordinary Rust references: compaction can move
   objects, and the guest stack and heap share one bounded Wasm memory.

Safe Rust can surround the engine, but the compact core will necessarily have
small, reviewed unsafe sections. Pointer arithmetic should be concentrated in
arena and representation modules rather than repeated throughout semantics.

## Phase 1: establish substitution tests

1. Keep the existing C engine as the semantic and performance baseline.
2. Expand the direct lifecycle test to cover compile, relocate, load, run,
   exception, and context destruction as data-driven operations.
3. Add mixed-build selection at a single function boundary at a time.
4. Record deterministic results rather than internal addresses or formatted
   diagnostics. Add structural assertions only after Rust owns a subsystem.

This phase has begun: the engine test already compiles source to bytecode,
destroys the compiler context, loads it into a fresh context, and runs it.

## Phase 2: finish allocation-free libc ponyfills

Implement the simplest C-compatible operations first:

1. Complete and exercise byte and string primitives. `memcpy`, `memmove`,
   `memset`, `memcmp`, and `strlen` are already implemented.
2. Add small character classification and conversion functions only when the
   C sources require them.
3. Replace straightforward formatted-output helpers with bounded Rust writers
   where doing so does not change formatting semantics.
4. Keep `setjmp`, floating-point environment details, and allocation out of
   this phase; they affect control flow or the engine's physical memory model.

Each ponyfill should have a table of inputs, mutations, return values, and edge
conditions, plus a Wasm inspection proving that it did not introduce imports.

## Phase 3: port independent utility algorithms

These functions operate on caller-owned bytes and have little engine state:

1. UTF-8/WTF-8 encoding, decoding, scanning, and hexadecimal conversion from
   `cutils.c` and `cutils.h`.
2. Endian, unaligned-load, bit-counting, rotation, and sign-extension helpers.
3. Bounded string helpers and representation-preserving float bit conversions.
4. Intrusive-list operations, represented initially as pointer operations over
   the existing C nodes rather than a new Rust collection.

The public C symbols remain thin entry points so C callers do not change yet.

## Phase 4: port self-contained numeric subsystems

1. Port number parsing and formatting from `dtoa.c` behind its existing API.
2. Compare every formatting mode, radix, rounding boundary, NaN, infinity,
   overflow, and underflow case against C.
3. Port the compact `libm` functions in groups of shared reduction kernels.
4. Leave soft float as a separate optional milestone; do not mix its template
   translation into the first native-float replacement.

These ports may allocate temporary Rust values outside the JavaScript arena
only when that cannot become hidden persistent guest memory. A no-allocation
implementation remains preferable for predictable Wasm limits.

## Phase 5: define Rust representations without changing ownership

Introduce one internal Rust module for the physical engine model:

- tagged `Value` encoding and immediate-value operations;
- block tags, sizes, alignment, and checked offset arithmetic;
- borrowed `ContextView`, `HeapView`, and `StackView` types;
- temporary rooted-value guards that map directly to the C root chain;
- explicit conversion at every C ABI boundary.

Mirror stable C structures directly where that makes shared-memory operation
simpler. Ordinary records can use `#[repr(C)]`; tagged unions can use a
`#[repr(C)]` union behind a small unsafe accessor; and trailing variable-size
data should be represented as a fixed header plus an explicitly bounded slice.
Do not hand-copy layout assumptions without checking them. A small C layout
probe and Rust tests should compare, for every mirrored type:

- total size and alignment;
- each shared field's byte offset and size;
- pointer width and the selected 32- or 64-bit value representation;
- constants for tags, classes, flags, and discriminants.

Compile-time C assertions should catch drift when possible. Generated layout
facts are acceptable as test/build input, but the maintained Rust structures
should remain readable rather than becoming a large generated binding file.

Some structures should initially remain opaque. C bitfields, flexible array
members, conditionally compiled fields, and unions whose active member is
implied by a separate tag are the likely trouble spots. Mirror these only after
their invariants are documented. Prefer integer flag words with accessors over
Rust bitfields, and prefer offsets into the supplied arena over native pointers
in serialized forms.

At this stage the mirrored types still view C-owned memory. They must not expose
Rust references that outlive an allocation or collection point. C and Rust may
also alias the same structure, so mutations cross the boundary through narrow
functions or short-lived raw-pointer views—not simultaneous long-lived `&mut`
references. Operations that can allocate should require handles or offsets and
should make invalidation visible in their signatures.

Mirroring first is valuable even where the final Rust representation changes:
it lets individual functions move between languages without translating the
whole object graph, and it gives the mixed engine one physical source of truth
rather than synchronized duplicate structures.

## Phase 6: move leaf heap values behind the views

A tentative order is:

1. Numeric boxing and unboxing.
2. Byte arrays and tagged value arrays.
3. String allocation, traversal, comparison, slicing, and the position cache.
4. Atom lookup and interning.
5. Basic object allocation without property mutation.

The C allocator and collector still own all storage. This phase tests whether
the views and root guards describe real lifetimes before they become ownership
machinery.

## Phase 7: rewrite arena allocation and roots

First reproduce the existing upward heap and downward stack rather than
designing a general allocator. Replace, in order:

1. alignment, block-header access, and collision checks;
2. upward allocation and the limited shrink/free operations;
3. root-chain insertion and removal;
4. context initialization and teardown around the bounded region;
5. debug validation of every block, root, stack slot, and handle.

The arena should be parameterized by a byte slice or Wasm linear-memory range.
It should not call Rust's global allocator for guest objects. Generation-tagged
handles may be useful for host/debug APIs, but the compact interpreter path may
continue to use validated offsets where that is measurably smaller and faster.

## Phase 8: rewrite garbage collection and compaction

This is the first major ownership milestone and should remain separate from
objects and interpreter semantics:

1. object-size discovery and root marking;
2. reachability through each existing block tag;
3. weak/ephemeron propagation;
4. finalization and sweeping;
5. in-place compaction;
6. rewriting every heap, stack, context, and bytecode pointer;
7. adversarial collection at every allocation boundary in debug tests.

Only after mixed runs produce the same observable finalizer and weak-reference
traces should the C allocator and collector be removed.

## Phase 9: objects, properties, and closures

Rough order, to be refined after the arena work:

1. ordinary objects and dense arrays;
2. property hashing, lookup, definition, deletion, and enumeration;
3. prototypes, accessors, strings, and typed-array special properties;
4. global and lexical lookup;
5. closure environments, captured variables, and callable objects;
6. iterators, collections, weak collections, and promise storage.

This phase should favor shared primitives over one translation per JavaScript
built-in, while retaining the compact layouts until measurements justify a
change.

## Phase 10: bytecode loading and interpreter

Tentative sequence:

1. bytecode header validation, decoding, and relocation;
2. stack frames, calls, returns, and exceptions;
3. constants, locals, globals, and branches;
4. property and iterator opcodes;
5. arithmetic, comparison, and coercion slow paths;
6. suspension, resumption, jobs, and later `await` support.

The opcode table should remain the shared declarative source while C and Rust
interpreters coexist. Differential tests should run identical bytecode images,
not compile the source separately for each interpreter.

## Phase 11: parser and compiler

This order is provisional:

1. source positions, diagnostics, and lexer;
2. bytecode emitter, labels, constant pools, and source maps;
3. expression parser and its explicit continuation frames;
4. statements and control flow;
5. functions, closures, classes, and destructuring;
6. bytecode analysis, compaction, and serialization;
7. JSON and RegExp literal entry points.

The existing recursion-free parser is part of MicroQuickJS's bounded-memory
design and should be preserved before considering more idiomatic Rust parser
structures.

## Phase 12: built-ins and regular expressions

Still rough and subject to reordering:

- Move native built-ins by dependency group, beginning with Object and basic
  primitive wrappers, then Array/String, typed arrays, Math, JSON, and Date.
- Translate the bundled RegExp compiler and VM as their own subsystem after
  strings, bytecode conventions, and arena ownership are stable.
- Keep the ROM standard-library builder usable throughout. A Rust replacement
  for it is useful, but it is not on the runtime's critical path.

## Completion criteria

The rewrite is complete when the Rust engine can build and consume compatible
bytecode, passes the C behavioral corpus and structural memory tests, stays
inside its supplied Wasm memory, and meets agreed size and speed bounds. The C
implementation may remain as a readable oracle and provenance source even
after it is no longer linked into the product build.

# Testing strategy

The tests preserve behavior at several boundaries so replacing C does not
require preserving its internal structure.

## Ponyfill contracts

Table-driven native Rust tests exercise each C-compatible function directly.
Cases are data—inputs, operation, and expected result—while a thin runner owns
the unsafe calls. Tables cover return values, mutation, overlap rules, boundary
lengths, and byte values outside ASCII. This makes individual Rust replacements
cheap to review without growing a forest of one-off test functions.

## Mixed-engine substitutions

Wasm builds replace one C subsystem at a time. The same MicroQuickJS tests run
against the unmodified C subsystem and its Rust replacement. This locates a
regression without requiring the eventual Rust design to resemble the C code.

## JavaScript behavior

Prepared bytecode programs record observable results rather than heap layout:

- values, exceptions, and coercions;
- property order and descriptors;
- calls, closures, and control flow;
- garbage-collection and finalizer effects;
- strings, regular expressions, and numeric edge cases.

Programs and their expected observations live in versioned corpus files. A
manifest selects required capabilities, entry bytecode, inputs, and expected
trace. The runner contains little case-specific logic. Each case runs against
the C baseline, mixed C/Rust builds, and eventually the Rust engine. Results use
a small deterministic binary trace, not formatted diagnostic text. This suite
is the bridge to Rust-owned arenas, lifetimes, and enums because those
representations may change while the trace remains equal.

## Structural Rust tests

Once a subsystem is Rust-owned, additional tests may assert invariants the C
implementation cannot express: generation validity, arena ownership, absence
of dangling references, and deterministic reclamation. These complement the
behavior suite; they do not replace it.

The library has no product `main`. Native unit tests use Rust's generated test
harness. Wasm integration tests will expose narrow test entry points and use a
separate runner.

# MicroQuickJS Experiment

This directory preserves a runnable research prototype formerly called
MicroESNext. It explores a Rust-native JavaScript engine inspired by
[MicroQuickJS](https://github.com/bellard/mquickjs), including four-byte tagged
values, relocatable word offsets, a bounded address space, stack bytecode, and
guest calls that do not recurse through the native stack.

This is not a complete or conforming JavaScript engine. It is kept because its
tests and browser demos exercised useful ideas: removable language
capabilities, a `no_std` interpreter, asynchronous suspension represented in
VM frames, host references, and CodeMirror running through a sandboxed DOM
bridge. The internal crate and API names remain `microesnext` so the research
artifact stays runnable without a disruptive cosmetic rewrite.

## Status and scope

The prototype is wrapped up rather than developed toward production. Changes
should be limited to keeping its existing tests and demonstrations runnable,
fixing a regression that blocks a documented demonstration, or improving the
accuracy of this record. Passing tests prove only the behavior they exercise.
They do not establish ECMAScript conformance, memory safety for arbitrary
programs, or suitability for hostile code.

The wrap-up demonstration is the three-file tabbed CodeMirror example with
search across files. It also runs on the repository's QuickJS and MicroQuickJS
runtimes, making it a useful differential fixture. The larger `full` page is
preserved as an incomplete stress fixture, not a wrap-up requirement: opening
search after its completion and folding interactions can still expose a raw
getter to numeric coercion and stop the guest. The prototype remains
observably slower than MicroQuickJS in this workload, and interaction testing
has uncovered semantic and lifetime bugs that unit tests did not predict.

Run the focused regression suite used by the wrap-up with:

```sh
cd dev/microquickjs-experiment
cargo test -p microesnext --features full --test host-define-property
```

The package-level preservation suite also builds the retained C reference and
passes with:

```sh
npm test
```

Build the CodeMirror artifacts from the repository root with:

```sh
CODEMIRROR_TARGETS=multi \
  node dev/wasm-web-runtimes/examples/codemirror/build-wasm.js
```

The browser regression tests are:

```sh
node --test \
  dev/wasm-web-runtimes/examples/codemirror/test/multi-browser.test.js
```

A comprehensive `cargo test --workspace --all-features` is intentionally
recorded as non-green: it reaches
`computed_object_properties_use_object_keys_not_array_offsets` and exhausts
that test's small fixed arena. Bare `cargo test --workspace` also attempts to
compile feature-dependent integration tests against the empty default feature
set because those tests do not declare Cargo `required-features`. These are
preserved limitations, not wrap-up gates.

## Memory-management limitation

The Rust-native implementation does **not** reproduce MicroQuickJS's compact
memory system. Similar vocabulary and four-byte values should not obscure the
difference. In particular, this prototype does not exactly reproduce
MicroQuickJS's:

- single compact heap and opposing VM-stack layout;
- internal pointer and offset representation;
- complete root set and rooting lifetimes;
- allocation and object lifetime rules;
- mark traversal and garbage-collection behavior; or
- pointer-threaded relocation and in-place heap compaction.

The prototype instead composes Rust crates around its own arena, roots, block
kinds, and feature boundaries. That made isolated ideas easy to test, but it
also introduced abstraction boundaries and bookkeeping that differ from the
engine used as inspiration. Correct behavior in a small test therefore does
not prove that a reference remains valid through every allocation, callback,
or collection point. This architectural mismatch is also a likely contributor
to the CodeMirror performance gap; it should not be papered over with isolated
micro-optimizations.

## Correctness and performance record

- The parser and compiler implement a deliberately incomplete subset of
  JavaScript. Unsupported and untested syntax remains unsupported.
- Host-object, event, accessor, selection, drag, timer, and garbage-collection
  interactions have required fixes discovered through browser use.
- The full CodeMirror fixture is preserved specifically because it exceeds the
  supported demonstration and records remaining failures. It is not a claim
  that arbitrary CodeMirror extensions or browser applications work.
- The capability crate graph grew more elaborate than the corresponding
  compact MicroQuickJS mechanisms. Feature isolation measurements are useful
  research data, but the number of boundaries is not the desired final design.
- Browser startup and editing are slower than the MicroQuickJS demonstration.
  No stable performance guarantee is recorded for this prototype.
- The old C sources under `src/` are reference material. The Rust engine does
  not share a live MicroQuickJS context with them.

## Next experiment: replace MicroQuickJS in place

The follow-up should begin with an exact C build of MicroQuickJS, including its
real allocator, heap, stack, roots, garbage collector, and compactor. Its build
should follow the working MicroQuickJS runtime in
`dev/wasm-web-runtimes/examples/microquickjs-suite/microquickjs-guest-runtime`:
compile the vendored C engine and the small Rust/Wasm boundary into one module,
then load ordinary MicroQuickJS bytecode. Rust code will share the live
machine's `JSValue`s, pointers or offsets, heap, VM stack, and roots—not
communicate with a second engine over RPC.

The intended destination is a complete rewrite in Rust, reached incrementally
rather than by constructing another engine beside MicroQuickJS. C remains the
working migration substrate until each bounded replacement is proven. During
that process MicroQuickJS's large C translation unit may be split into focused
C files to improve navigation and auditing without changing its representation
or behavior. Such moves need mechanical or differential verification so code
organization is not confused with an engine rewrite.

The first Rust crate should be a small, explicitly unsafe compatibility layer
over the exact C layouts and operations. Persistent identities remain traced
MicroQuickJS values or offsets. A raw pointer or Rust reference must never
survive an operation that can allocate or collect; code must root the value and
reacquire its address afterward.

Groups of functionality may have parallel C and safe-Rust implementations in
the same process. A build-time choice or narrow dispatch point can run either
implementation against the same representation. Differential tests should
compare results, exceptions, roots, and heap invariants before the C version is
removed. Performance-critical loops may use narrowly scoped unsafe Rust when
measurement justifies it, while the bulk of each replacement can use safe Rust
above the compatibility layer.

The allocator and collector should be among the last systems replaced. This
keeps every earlier change grounded in MicroQuickJS's actual memory semantics
and avoids constructing another engine that merely resembles it. ESNext
features should begin only after the unchanged C baseline and each replacement
stage pass the same bytecode, behavior, compaction, and browser-demo tests.

## Implemented capability inventory

The list below records experiments present in the prototype. It is an inventory
of code and feature gates, not a completeness or conformance statement.

## Crates and removable capabilities

- `microesnext-types` defines the four-byte `Value` and `HeapRef` words.
- `microesnext-arena` owns the fixed-capacity heap and VM stack and compacts
  references without a forwarding-table allocation.
- The bytecode `core` module defines the raw opcodes and readers used by the
  invariant interpreter loop. It has no capability features; its immediate
  opcode covers `undefined`, `null`, and booleans in every build.
- `microesnext-bytecode` adds the typed instruction vocabulary used by tools
  and the capability wrapper. Its optional opcode groups follow the runtime
  capabilities, so an omitted feature does not enlarge its valid enum surface.
- `microesnext-compiler` contains allocation-using source and bytecode tooling;
  the runtime crates do not depend on it. Its syntax families are progressively
  feature gated too: reduced builds leave omitted syntax to the ordinary parse
  error at that character rather than retaining feature-specific diagnostics.
  Source positions are a separate authoring feature. Zero-argument functions,
  parameter/argument frames, captured-environment analysis, synchronous named
  recursion, and asynchronous named recursion are independently selectable,
  mirroring their runtime instruction groups. Quoted and no-substitution
  template strings enter only with the string bytecode capability. The
  compiler-only `literal-expressions` composition upgrades numeric-only array
  and object values to arbitrary supported expressions while preserving the
  smaller specialized literal loops when omitted.
- The values `strings` feature supplies ordinary packed byte strings, strict
  allocation-conscious concatenation, and an atom-table module. The VM retains
  atom state only when its `atoms` feature is selected; ordinary string literals
  neither allocate nor populate that table.
- `microesnext-objects` supplies prototype and property-table storage. Its VM
  feature composes strings for JavaScript property names, while the low-level
  crate can also use already-interned or non-string keys. A separate
  `property-assignment` bytecode/compiler gate adds source statement writes;
  read-only object builds retain no write dispatch beyond literal assembly.
- The objects `prototype_chain` module performs allocation-free traversal for
  `instanceof` and `Object.prototype.isPrototypeOf`; the VM feature determines
  whether any traversal call is retained.
- The objects `instanceof` module composes callable validation, ordinary
  `prototype` lookup, and traversal without allocation. Custom
  `Symbol.hasInstance` dispatch remains a higher optional layer.
- The arena's gated `closures` module stores closure entries and captures for
  builds enabling the `functions` feature. Closure storage is not a separate
  semantic library; direct calls still remain in the base VM for now.
- The objects `callable` module optionally wraps a compact closure in an
  ordinary property-bearing object. Calls unwrap it at a statically selected
  boundary. Its constructor path creates the `.prototype` / `.constructor`
  cycle in fixed arena records; closure-only and object-only machines retain
  their specialized paths and layouts.
- The objects `construction` module creates an ordinary receiver from a
  constructor's current prototype and applies the object-return rule. The VM
  composes it with receiver frames using two gated opcodes, without persistent
  machine state or changes to the invariant call frame.
- The objects `class_constructor` module gives classes a distinct object record.
  A class can use the same removable construction path, but ordinary call
  unwrapping does not accept it. The initial `classes` compiler slice supports
  constructor-only declarations; methods and inheritance remain separate.
- The objects `method_calls` module preserves a member receiver beneath its
  resolved method and removes both before entering the call frame. The independent
  `class-methods` composition stores receiver-aware, non-constructible callable
  objects on a class prototype; constructor-only class builds retain neither
  its stack operations nor its three opcodes.
- The arena's `stack-operations` feature supplies removable operand duplication
  and discard helpers. Class expressions duplicate their class record only
  while installing properties. The separate compiler-only
  `expression-statements` gate emits a generic discard for any supported
  expression followed by `;`; it does not reuse exception unwinding or add a
  statement-specific path to each expression capability.
- `class-default-constructors` is compiler-only: it synthesizes the same compact
  receiver-aware body and class-record opcode sequence when a base class omits
  `constructor`. Explicit-constructor compiler builds do not retain that parser
  branch or synthesis code, and the runtime has no corresponding feature.
- `conditional-expressions` is likewise compiler-only. It emits the existing
  typed truthiness and jump vocabulary for `condition ? consequent : alternate`,
  so removing the parser branch changes no runtime dispatch path.
- `nonterminal-conditionals` lets either side of `if`/`else` join later
  statements, while omitting the join jump after an abrupt branch. It reuses
  control-flow bytecode and relocates both targets inside function bodies;
  reduced control-flow compilers retain their smaller terminal-only parser.
- `nested-conditionals` replaces recursive descent through conditional blocks
  with explicit consequent/alternate frames in the compiler's allocation-using
  worklist. Thousands of nested source branches therefore do not consume the
  Rust stack, while nonnested compiler builds omit the frame type and loop.
- `nested-loops` generalizes that worklist with loop frames, so arbitrarily
  interleaved `while` and `if` blocks compile without Rust recursion. It emits
  the existing control-flow vocabulary; builds that stop at nested
  conditionals retain the smaller, conditional-only implementation exactly.
- `nested-exceptions` uses a separate explicit try/catch worklist and emits the
  existing optional handler bytecode. Returns close every live handler, throws
  retain the nearest handler, and omitting it preserves the smaller terminal
  exception parser rather than retaining dormant frame machinery.
- `nonterminal-exceptions` lets normally completed `try` and `catch` bodies
  join later statements. Its handler cleanup and jump patches compose into the
  nested worklist, while terminal-only exception builds retain neither control
  flow nor join bookkeeping.
- `implicit-completions` is compiler-only too. It lowers `return;` and a script
  or function body reaching its end to the invariant `undefined` constant and
  existing return instruction. Its omitted build retains the previous
  completion parser byte-for-byte rather than relying on optimization to erase
  a shared conditional branch.
- `class-static-methods` is also compiler-only. It installs the same
  non-constructible method wrapper directly on the class record instead of its
  prototype, so static calls reuse receiver-preserving method bytecode and
  observe the class as `this` without another runtime dispatch path.
- `class-expressions` accepts anonymous class values with explicit or implicit
  constructors and the same instance and static method compositions as class
  declarations. Named class-expression identity remains a separate future
  slice.
- The objects `recursive_constructor` module allocation-freely rebinds a named
  function expression's private self cell to its constructor wrapper. Ordinary
  constructors and recursive closures do not retain this cross-composition.
- `microesnext-bindings` groups feature-gated lexical and call-frame machinery
  that shares the same arena representation. Its `parameters` feature composes
  evaluated arguments with lexical slots; functions without arguments omit it.
  Its `receivers` feature adds hidden `this` values to selected call frames.
  Receiver slots live after ordinary locals, so existing local access remains
  unchanged and builds without methods or thenables omit that module.
- The bindings `environments` feature supplies traced one-value cells that
  genuinely escape into closures. The compiler shares a cell across sibling
  closures and outer writes; uncaptured locals remain direct stack words.
- The environments `assignment-expressions` feature stores through a cell
  while retaining the assigned value on the operand stack. The corresponding
  objects feature performs a result-preserving property store. Their dedicated
  inline operations leave ordinary assignment statements on smaller paths.
- The bindings `recursive-functions` feature composes closures with cells
  only for private self-bindings in named function expressions. Ordinary
  function builds do not retain the module or decode its constructor opcode.
- The execution `recursive-async-functions` feature performs the corresponding
  composition for named async expressions. It reuses async closure storage and
  an environment cell without entering ordinary recursive-function builds.
- The bindings `locals` feature supplies validated lexical stack slots. Loads and
  stores use bottom-relative positions, so temporary operands and suspension
  cannot move them; literal-only machines omit the bindings crate. The facade's
  `local-assignment-expressions` composition enables the arena's gated stack
  helpers, allowing an assignment to store one copy while returning the other
  without changing the local fast path.
- The semantics `integer-operations` feature supplies checked i30 negation,
  subtraction, multiplication, and relational comparisons. The bytecode and VM features
  decide which operations are reachable, so a unary-only build does not retain
  multiplication or comparison. `minimal-program` composes the same library
  with locals and control flow without adding floating-point storage or
  changing the invariant interpreter loop.
- `microesnext-semantics` interprets tagged values without owning their
  representations. Its independent `equality`, `truthiness`,
  `logical-operations`, and `typeof` features retain only the selected paths.
  Optional number, string, symbol, and callable-record features add the
  corresponding JavaScript behavior without indirect dispatch.
- The values `numbers` feature supplies heap-backed IEEE-754 representation together
  with its small division, negation, and primitive-coercion helpers. VM opcode
  selection and dead-code elimination remove unused operators; they do not need
  separate package boundaries. String coercion remains gated because it
  introduces the decimal parser. Integer-only builds do not link this module.
- The values `decimal-to-f64` feature is the shared, `no_std` decimal conversion
  boundary for source literals and string coercion. A small exact path handles
  common inputs; a bounded correctly-rounded fallback handles IEEE-754 edges.
  Builds omitting both consumers do not link the module.
- Numeric helpers retain the existing i30 fast paths. Overflow falls through to
  boxed values only when promoted operations are selected; decimal string
  parsing remains separately removable with its dependency.
- The values `symbols` feature supplies unique, relocatable property-key identities.
  Optional descriptions are ordinary values, so the feature does not force the
  string, atom, object, or collection capability into a symbol-only build.
- The symbols `well_known` module retains realm-owned identities. A realm can
  omit description strings or compose them without changing ordinary symbols.
- The objects `iterators` feature stores a source, cursor, and adapter tag in a
  relocatable guest object. Arrays and collections expose independently gated
  iterator modules, so adding array iteration does not pull in Map/Set storage,
  or the reverse.
- The collections `entry-iterators` feature adds pair-array allocation only
  for `Map.entries`; collection key/value and Set iteration do not link arrays.
- The iterator `results` feature allocates ordinary `{ value, done }` objects
  with cached property identities. Cursor-only builds do not acquire object,
  atom, or string storage. Its source-neutral boundary converts an adapter's
  `Option<Value>` into live or exhausted result objects.
- The iterator `protocol` feature defines and resolves realm-local
  `[Symbol.iterator]` bindings through object prototypes. Function validation
  and invocation remain independently composable.
- The semantics `equality` feature composes SameValueZero for enabled scalar
  types.
  Collections use raw compact identity in their standalone build; number and
  string comparison enters only when those capabilities are selected too.
- The objects `collections` feature contains ordered, geometrically grown Map and Set
  storage with live cursor semantics.
- The objects `arrays` feature contains dense and sparse indexed storage with geometric
  growth, holes, and JavaScript length behavior.
- The arrays `assignment-expressions` feature stores a computed index while
  retaining the assigned value. The compiler's separate `array-indexing` gate
  adds reads without runtime code; literal stores retain their smaller path.
- The collections module contains Map and Set plus an independently gated
  `weak` module. Ephemeron tracing is retained only by that feature.
- The execution `promises` feature contains compact promise records and a
  caller-owned, rooted FIFO job ring; it does not require a native allocator
  or Rust futures.
- The values `errors` feature supplies compact guest error identities without forcing
  message strings, stacks, objects, or exception handlers into every build.
- The Promise `resolution` feature optionally adopts native Promise results.
  Plain Promise storage does not retain the resolver path.
- The Promise `resolvers` feature adds compact guest-callable resolve/reject
  records. Each pair shares one arena cell, so exactly one call can win without
  allocating two independent closures.
- The scheduler `thenables` feature composes ordinary object lookup,
  receiver-aware calls, resolving functions, and deferred assimilation jobs. A controller
  schedules guest `then` code instead of running it during property resolution;
  resolving to another thenable produces another rooted job rather than native
  recursion. Builds without `thenables` link none of this composition.
- `microesnext-execution` contains the invariant interpreter core plus
  independently gated Promise state, exception handlers, stack suspension,
  async closure records, bounded caller frames, and recursive async
  construction. Promise-only users do not pull in bytecode or the core;
  ordinary synchronous machines retain none of the optional execution paths.
- `microesnext-vm` is the synchronous interpreter and suspension boundary.
- `microesnext-scheduler` contains independently gated async driving, Promise
  jobs, object-thenable jobs, and async-thenable resolution policies.
- The execution `async-functions` feature stores async closures and packages
  evaluated calls for independent guest contexts. Its bounded, caller-supplied
  frame stack connects nested calls to outer promises; caller suspension and
  promise orchestration remain absent from ordinary function builds.
- The scheduler `async-thenables` feature supplies a statically selected policy
  for object assimilation at both async return and `await`. Object operands use a
  small intermediate Promise and the bounded thenable-job queue; primitives
  and native Promises retain the ordinary path. The ordinary async driver
  remains monomorphized with its smaller native-Promise resolver when this
  composition is omitted.
- `microesnext` is a small facade; its `async` and `async-functions` features
  are disabled by default.

When source is compiled for a selected facade feature set, the source compiler
must enable the matching syntax and bytecode features. The facade's test-only
compiler dependency deliberately has no default features; each facade feature
forwards only its corresponding compiler feature. Production runtime builds do
not link the compiler, and reduced tests cannot accidentally emit bytecode for
a capability absent from their runtime.

The runtime is `no_std` and has no global-allocator or libc dependency. Its
arena borrows a caller-supplied word slice; only compiler tooling uses `alloc`.

These are static Rust feature and crate boundaries, not runtime plugins.
Release builds use fat LTO and one code-generation unit, so hot functions can
inline across them. Leaving out a capability removes its implementation without
adding indirect dispatch to the base interpreter.

`tools/measure-capabilities.ts` builds the isolated
`microesnext-capability-size` package, instantiates its final Wasm, calls every
claimed export, then reports raw and gzip sizes. The separate package has no
compiler dev-dependency whose Cargo features could contaminate production
measurements.

`tools/measure-compiler.ts` performs the corresponding check for the source
compiler. It links a real allocator-backed Wasm executable, instantiates it,
and requires the selected compiler to produce bytecode before reporting its
raw and gzip sizes. This avoids treating an archive or LLVM bitcode object as
evidence that omitted parser paths disappeared from a final program.

The isolated `microesnext-core-loop` package provides a repeatable native
instruction-loop check without compiler dev-feature unification:

```sh
cargo run --release -p microesnext-core-loop --no-default-features
cargo run --release -p microesnext-core-loop --no-default-features \
  --features arrays,control-flow,functions,number-division,number-remainder,objects \
  -- --machine
cargo run --release -p microesnext-core-loop --no-default-features \
  --features function-arguments -- --calls
cargo run --release -p microesnext-core-loop --no-default-features \
  --features environments,functions,locals -- --captures
npm run check:features
```

It is a regression signal rather than a claim that noisy wall-clock timings can
prove identical performance. The structural performance gate is stronger: the
minimal feature graph excludes capability modules, and the hot loop reads
raw opcode bytes from `microesnext-bytecode::core`. It uses a direct match with
no feature-dependent enum, trait objects, registries, or dynamic callbacks.
Only an extension byte crosses into the typed capability wrapper. Local and
control-flow instructions use that same static boundary. This keeps the raw
base loop byte-for-byte independent of those optional instruction families;
there is no trait object, registry, or runtime feature lookup.
`check:features` inspects Cargo's resolved graph and fails if representative
minimal or narrowly composed builds acquire unrelated capability features.

This is a new codebase. Existing MicroQuickJS runtimes elsewhere in the
Macchiato repository are consumers and comparison points, not source
dependencies. Integration happens only after the new runtime passes its own
tests.

# microesnext-regexp

A direct Rust translation of the compact regular-expression compiler and
interpreter embedded in MicroQuickJS.

The port preserves the source engine's bytecode model and ECMAScript behavior
instead of translating patterns into another regular-expression dialect. It is
`no_std`, uses only explicit caller-provided storage, and has no libc boundary.
The compiler and executor are separate features so a bytecode-only runtime does
not have to carry the parser.

During the port, differential tests compile and execute the same patterns with
the vendored C reference and this Rust implementation. The C reference is test
and provenance material; it is not linked into MicroESNext artifacts.

See [PROVENANCE.md](PROVENANCE.md) for the exact upstream source and license.



<!-- dev/microquickjs-experiment/crates/microesnext-regexp/TRANSLATION.md -->

# Translation workflow

The maintained implementation is a direct Rust port, not generated Rust checked
in without review. Mechanical drafts are useful for coverage and control-flow
comparison, so the workflow keeps them reproducible and separate from `src/`.

1. Run `tools/extract-reference.js` against the pinned `mquickjs.c`.
2. Translate the resulting compiler and executor units independently.
3. Use generated Rust only as a checklist and control-flow draft.
4. Replace C pointers, macros, allocation, and VM stack coupling with explicit
   Rust slices and caller-provided storage.
5. Differentially test patterns, bytecode, captures, errors, and timeouts
   against the pinned MicroQuickJS reference.

A whole-file C2Rust experiment was rejected: it imported unrelated VM code and
Clang 21's exporter could not represent parts of the translation unit. Isolating
the two regexp regions gives the translator smaller inputs and makes accidental
dependencies visible. Generated drafts belong in a sibling work directory, not
in this repository.

Oniguruma is intentionally out of scope until the MicroESNext runtime goal is
complete. Its separate crate remains a future optional backend and must not be
used to fill gaps in this port.

# Rust engine measurements

Measurements are checkpoints, not timeless claims. Keep the benchmark source,
command, host architecture, and feature set alongside results so later changes
can be compared honestly.

## Core opcode loop, 2026-08-25

The `core-loop` example ran 20,020,000 instructions per sample on
`aarch64-unknown-linux-gnu` with Rust 1.98.0, release fat LTO, and one codegen
unit.

| Build | Samples (ns/instruction) | Stripped executable |
| --- | --- | ---: |
| Minimal, no default features | 3.71, 3.81, 4.11 | 333,136 bytes |
| `async,objects,functions` | 3.53, 3.53, 3.57 | 333,136 bytes |

The timings are close enough that this run detects no feature-induced core-loop
cost; it does not prove mathematical equality. The identical executable sizes
occur because the example does not exercise capability code and fat LTO removes
it. `cargo tree --no-default-features` separately confirms that capability
crates do not enter the minimal dependency graph at all.

Future checks must include representative object, closure, collection, parser,
and suspension workloads and compare peak arena usage against upstream
MicroQuickJS. A faster synthetic addition loop cannot excuse regressions in
those workloads.

## Minimal programmable runtime, 2026-08-25

The smallest artifact remains a 1,984-byte (961 gzip) interpreter kernel. A
more useful minimum composes lexical locals, boolean control flow, checked i30
subtraction and multiplication, and relational comparison. Its live probe
executes the bytecode for a factorial loop guarded by `n > 1` and verifies the
result `720`.

| Build | Wasm bytes | Gzip bytes |
| --- | ---: | ---: |
| Interpreter kernel | 1,984 | 961 |
| Minimal programmable runtime | 6,506 | 2,526 |

The arithmetic implementation lives in `microesnext-integer-operations`; a
build omitting `minimal-program` neither resolves that crate nor decodes its
opcodes. This figure is a practical capability checkpoint, while the kernel
figure remains useful for measuring the fixed interpreter mechanism itself.

## Strict equality, 2026-08-25

The identity-only strict-equality build is 2,890 bytes (1,337 gzip). Its live
probe compares tagged booleans and its dependency graph omits string and number
storage. A number-only build is 7,484 bytes (3,261 gzip); its graph contains no
string, atom, or object crate and its live probe verifies that boxed NaNs remain
unequal. Composing both scalar representations produces a 9,480-byte (3,948
gzip) artifact whose additional probe verifies separately allocated equal
strings.

The semantics `equality` feature also retains SameValueZero for collection
keys, but the
VM's `===` and `!==` instructions call the strict operation. This avoids the
subtle but observable mistake of treating `NaN === NaN` as true while still
sharing the scalar decoding and string-content comparison machinery.

## Short-circuit logical operations, 2026-08-25

The immediate-only `&&`/`||`/`!` composition is 3,428 bytes (1,647 gzip). Its
live probe short-circuits over a throwing right operand, verifies that the left
operand is preserved, and then negates it. Optional scalar truthiness remains
independent:

| Build | Wasm bytes | Gzip bytes |
| --- | ---: | ---: |
| Logical operations | 3,428 | 1,647 |
| Bounded numeric negation | 2,587 | 1,279 |
| Logical operations with numbers only | 7,502 | 3,268 |
| Logical operations with strings only | 7,151 | 3,096 |

The number-only dependency graph contains no string crate, and the string-only
build contains no number crate. Macro-generated crate tests exercise each side
alone and together. Adding the capability leaves both the 1,984-byte kernel and
the 6,506-byte minimal programmable runtime byte-for-byte unchanged.

## Primitive Number coercion, 2026-08-25

The standalone primitive-coercion build is 6,371 bytes (2,823 gzip). Its live
probe executes `+true` and verifies the immediate result `1`; runtime tests
also cover false, null, undefined/NaN, i30 values, and existing boxed numbers.
It contains number representation but neither integer operations nor either
negation path. The compiler-only unary-plus build is 5,690 bytes (2,466 gzip).

Number negation now composes the same coercion crate, making `-true`, `-null`,
and `-undefined` follow primitive JavaScript semantics. Its linked artifact is
6,898 bytes (3,040 gzip). The pre-existing i30 branch remains a direct fast
path, and the interpreter kernel, bounded-negation, promoted-operations,
and minimal-program artifacts are byte-for-byte unchanged.

## String Number coercion, 2026-08-25

The string composition is 14,599 bytes (6,608 gzip), while its compiler gate
is 6,553 bytes (2,932 gzip). The runtime parses the complete decimal shape,
signed `Infinity`, binary/octal/hex integer forms, negative zero, and the
current ECMAScript whitespace set without a temporary allocation. Power-of-two
radices retain guard and sticky bits for ties-to-even conversion rather than
repeatedly rounding a growing float. Invalid strings produce NaN.

`microesnext-decimal-to-f64` now supplies an allocation-free, `no_std`, compact
correctly-rounded conversion shared by source literals and string coercion.
It uses an exact common-input path and a 768-digit bounded fallback based on
Nigel Tao's Simple Decimal Conversion. Differential tests cover 40,000 random
decimal strings, 100,000 finite-float display round trips, long truncated
inputs, subnormal boundaries, overflow, and ties. This replaced Rust core's
larger generic parser: before the replacement the same string composition was
29,262 bytes (20,113 gzip).

Five native release runs put the common path at a median 7.5 ns per conversion,
versus 6.6 ns for `str::parse::<f64>` on this machine. The deliberately compact
fallback is much slower—about 4.04 us versus 21.5 ns—so ordinary literals avoid
it when their mantissa is exactly representable and their decimal exponent is
within ±22. Run `cargo run --release -p microesnext-decimal-speed` to reproduce
the directional comparison; it is a microbenchmark, not a cross-machine claim.

The cost remains confined to its static capability boundary. Primitive
coercion is still exactly 6,371 bytes, Number negation is still exactly 6,912
bytes, and builds without decimal literals or string coercion neither resolve
the conversion crate nor execute a dispatch branch for it.

## Division and remainder, 2026-08-25

The division-only runtime is 6,494 bytes (2,878 gzip), compared with 5,311
bytes (2,422 gzip) for number storage alone. Remainder is independently 9,311
bytes (4,240 gzip). An initial combined implementation measured 9,786 bytes
(4,363 gzip): linked measurement revealed that `%` retained a much larger
floating helper and would make `/` pay for it. The final design therefore uses
two leaf crates, two bytecode gates, and compile-time VM arms.

Compiler probes are 9,478 bytes for each isolated token family (4,401 gzip for
division and 4,402 for remainder); most of that build is their shared decimal
literal parser. Feature-graph checks prove that either compiler gate includes
`numbers` but neither integer operations nor the other quotient operation.
The existing number-operations runtime remains exactly 9,382 bytes and the
minimal runtime remains exactly 1,984 bytes.

Four alternating native runs after the split measured the invariant `Core` at
3.05–3.37 ns/instruction in the minimal build and 3.04–3.07 with division,
remainder, arrays, control flow, functions, and objects enabled. The typed
`Machine` path measured 3.05–3.22 minimal and 3.04–3.23 composed. The overlap
does not prove identical timing, but it detects no regression; more
importantly, the omitted build has neither crate nor typed match arm.

## `typeof`, 2026-08-25

The isolated runtime is 6,642 bytes (3,024 gzip), including ordinary string
storage and a live probe that checks `typeof true === "boolean"` by content.
The compiler is 6,554 bytes (2,940 gzip), only 201 raw bytes above its
string-literal build. Its optimized keyword-only unary scanner remains
separate from the mixed-operator scanner; builds omitting `typeof` preserve
their pre-existing parser paths.

The base classifier recognizes immediates, strings, ordinary objects, and
closures. Cargo weak-feature forwarding adds boxed numbers, symbols, async
closures, and Promise resolvers only when those representations coexist.
Feature-graph checks show that `typeof` alone includes neither numbers,
objects, arithmetic, atoms, nor string concatenation.

Four alternating native runs measured minimal `Core` at 3.07–3.08
ns/instruction and a broad build including `typeof` at 3.04–3.33 (one broad
outlier; the other samples were 3.04–3.05). `Machine` measured 3.06–3.07
minimal and 3.06–3.12 broad. As with the other timing gate, the structural
evidence is definitive: omitted builds have no classifier crate or opcode arm.

## Ordinary `instanceof`, 2026-08-25

The checked editor bundles contain 30–136 `instanceof` occurrences each. Its
semantic path is consequently composed from separately removable callable
objects, property lookup, and prototype traversal rather than folded into the
object representation. A callable-object artifact is 17,812 raw / 7,107 gzip
bytes; adding the operator, its interned `prototype` key, and an executed probe
is 20,311 / 7,791, an increment of 2,499 raw / 684 gzip bytes.

The standalone compiler is 5,956 raw / 2,586 gzip bytes. Its keyword-only
relational parser remains independent of numeric comparisons, while a build
containing both preserves left-associative relational order. Builds omitting
`instanceof` retain their prior specialized parser, and the objects-only Wasm
remains exactly 14,473 / 5,775.

Constructible function records are separately gated. Adding their opcode,
interned `prototype` and `constructor` keys, fixed cyclic allocation, and live
probe to callable objects produces 20,106 raw / 7,695 gzip bytes—2,294 raw /
588 gzip incremental. The compiler's constructor form is 13,264 / 5,615.
Source-to-VM tests verify the
prototype cycle and that arrows do not acquire the constructor opcode.

Ordinary instance construction is another composition rather than constructor
baseline code. Its live Wasm probe, receiver-aware call path, receiver creation,
and return selection total 27,444 raw / 9,825 gzip bytes. Its refactored
compiler slice is 15,459 / 6,311 and accepts direct calls with arguments while
being 81 raw / 115 gzip bytes smaller than the initial direct-call parser. The
source-to-VM tests exercise `this`, primitive fallback, explicit object returns,
the resulting prototype chain, member constructor lookup, and postfix access to
the selected result. Builds omitting `construction` do not decode its two
opcodes or retain the objects construction module; the constructor-only compiler stays
exactly 13,264 / 5,615.

The constructor-only `classes` composition uses a distinct class record while
reusing receiver frames and ordinary construction. Its live runtime is 30,301
raw / 10,377 gzip bytes and its compiler is 19,762 / 7,588. The object-only
probe remains exactly 14,473 / 5,775 and ordinary construction remains exactly
27,444 / 9,825 when class support is omitted.

The independent `class-methods` composition is 32,689 raw / 10,891 gzip bytes;
its compiler is 20,727 / 7,869. It covers method wrapping, receiver-preserving
lookup and calls, method parameters, and non-constructibility. With that feature
omitted, the constructor-only runtime remains 30,301 / 10,377 and its compiler
remains 19,762 / 7,588.

Implicit base constructors are compiler-only. Their focused build is 20,541
raw / 8,091 gzip bytes. Omitting the feature leaves the explicit constructor
compiler exactly 19,762 / 7,588 and changes no runtime artifact. The default
compiler includes this syntax without adding a runtime feature.

Static methods are another compiler-only selection over the existing method
runtime. Their focused compiler is 20,844 raw / 7,916 gzip bytes. Omitting them
leaves instance methods exactly 20,727 / 7,869. The default compiler including
static methods reuses the same runtime operations.

Anonymous class expressions add one removable operand-stack operation so the
class record can remain as the expression result while methods are installed.
The live runtime composition is 33,060 raw / 11,025 gzip bytes and its compiler
is 23,379 / 8,866. Omitting it leaves the class-method runtime exactly 32,689 /
10,891 and its compiler at 20,727 / 7,869. With expressions
included, the default compiler is 48,615 / 17,302 and the all-capability runtime
is 109,821 / 34,862.

Private identity for named constructor expressions is separately removable.
The `recursive-constructors` composition is 23,517 raw / 8,554 gzip bytes and
its compiler is 18,137 / 7,564. Its allocation-free opcode changes capture zero
from the compact recursive closure to the wrapper; declarations continue to use
their existing captured destination cell. Builds selecting ordinary recursive
functions or non-recursive constructors do not link this bridge crate.

Property-assignment statements reuse the ordinary object store behind one
independently decoded opcode. The live runtime composition is 16,352 raw /
6,302 gzip bytes; its compiler is 11,317 / 4,571. The end-to-end constructor
test passes an argument into `this.answer = value`, returns a primitive, and
reads the initialized property from the preserved receiver. Object builds that
omit this source operation do not decode its opcode.

## Feature-independent core, 2026-08-25

After Promise jobs were added, the facade benchmark began varying with enabled
features even though it executed only integer opcodes. The hot interpreter was
first extracted into `microesnext-vm-core` and now lives in the independently
gated execution `core` module; its byte readers and raw base-opcode constants
live in the bytecode `core` module. Neither core layer has capability features.
Optional opcode bytes return to the typed VM wrapper;
base bytecodes remain in a state type and dispatch loop whose compiled Rust
surface does not vary with the selected capabilities.

An isolated `microesnext-core-loop` package prevents the compiler dev
dependency from unifying all facade features into the benchmark. That exposed
a real 10–30% regression hidden by the earlier setup. Disassembly showed fat
LTO declining to inline base call-frame setup in the larger build, which added
register spills to unrelated arithmetic dispatch. Keeping that small base
operation always-inline restored overlapping minimal and full measurements.

Eight alternating samples in the latest run measured 3.30–3.47 ns/instruction
for minimal `Core` and 3.47–3.51 for full `Core`; `Machine` measured 3.29–3.81
for minimal and 3.29–3.53 for full. Process startup, frequency scaling, and
separately linked layouts make these samples noisy. They detect no consistent
capability penalty, but do not prove mathematical equality. The stronger gate
is structural: optional crates and their typed opcodes cannot enter the raw
base loop.

# Bytecode study

MicroESNext inherits MicroQuickJS's compact stack bytecode. Instructions have a
one-byte opcode followed by zero, one, two, or four bytes of immediate data.
`mquickjs_opcode.h` is the authoritative instruction list: it declares each
instruction's encoded size, stack inputs and outputs, and operand format. The
same table drives interpretation, stack-depth analysis, relocation, dumping,
and 64-to-32-bit bytecode conversion.

Function bytecode carries a constant pool, argument and local-variable names,
captured-variable descriptors, a maximum operand-stack depth, source mapping,
and nested function bytecode. `fclosure` instantiates a nested function and
connects its captured variables to the enclosing frame. Calls, returns,
exceptions, and `finally` already have direct instructions.

## Arrow functions

Arrow functions do not require a new instruction. Their parameters and body
use ordinary function bytecode, and `fclosure` creates the function. A function
metadata bit distinguishes arrows so closure creation captures the enclosing
`this`, calls restore that captured value, and construction can be rejected.
Expression bodies compile as an expression followed by `return`.

## Named function expressions

A named expression has a lexical self-binding that is not visible in its
enclosing scope. The optional `recursive_closure` instruction composes the
ordinary closure and environment-cell capabilities: it creates one cell,
places it first in the capture list, constructs the closure, and initializes
the cell with that closure. Unnamed expressions, arrows, and declarations do
not pay for this constructor, and builds omitting `recursive-functions` reject
its opcode.

## Class constructors

`to_class_constructor` wraps a compact closure in a distinct property-bearing
record and creates its `.prototype.constructor` cycle. The ordinary call path
does not unwrap this record; the independently gated construction path does.
Constructor-only class declarations otherwise reuse receiver frames, argument
calls, property stores, and return selection rather than adding a parallel
execution model.

The compiler emits `construct_value_arguments` and
`select_constructed_result` before compiling any later property or call
suffixes. Constructor-member lookup uses ordinary `get_property`, because
`new namespace.Type()` constructs the resolved value rather than calling it as
a method of `namespace`. The selected instance or explicit object result then
enters the unchanged postfix path, allowing forms such as `new Type().read()`.

An omitted base constructor needs no bytecode extension. When enabled, the
compiler synthesizes an ordinary zero-parameter receiver frame ending in
`load_this` and `return_receiver_locals`, then applies `to_class_constructor`.
This keeps implicit construction entirely out of runtimes that only consume
explicitly authored bytecode.

The separate method composition uses `to_method`, `get_method`, and
`call_method_arguments`. `get_method` preserves the base immediately below the
resolved value; evaluated arguments follow it. The call instruction removes the
method and base, appends the base as the hidden receiver only for a callable
object, and enters the otherwise ordinary argument frame. Omitting method calls
leaves `get_property` and ordinary call bytecode unchanged.

Static methods require no fourth method opcode. The compiler selects the class
record rather than its `prototype`, applies `to_method`, and stores the result;
subsequent member calls use the same `get_method` and `call_method_arguments`
sequence as instance methods.

Anonymous class expressions use the independently gated `duplicate_top`
instruction while installing methods. The original class record stays beneath
the duplicate, decoration consumes the duplicate, and the original becomes the
expression result. A class with no methods needs no duplication. This avoids a
persistent temporary local and leaves declaration-only class bytecode and its
runtime unchanged.

Uncaptured local assignment expressions reuse that same `duplicate_top`
instruction. The right-hand value is duplicated, `store_local` consumes one
copy, and the other remains as the expression result. Statement assignment
continues to emit only `store_local`; builds omitting assignment expressions do
not decode stack duplication merely because they support mutable locals.

Captured assignment uses `store_environment_cell_result` instead. Its input is
`[cell, value]` and its output is `[value]`; the operation updates the traced
cell between those states. This is deliberately distinct from
`store_environment_cell`, which consumes both inputs for statement assignment,
and from `duplicate_top`, which cannot preserve a value around a cell without
extra stack movement.

Property assignment expressions use `set_property_result`. Its input is
`[object, key, value]` and its output is `[value]`; the object store occurs
between those states. Intermediate dot segments use ordinary `get_property`,
so a nested target adds no specialized traversal instruction. The opcode is
separate from `set_property`, which returns the object for literal assembly,
and `set_property_statement`, which leaves no result.

Computed array reads use the existing `get_index` instruction already required
by array storage. The compiler-only `array-indexing` gate therefore changes no
runtime. Array assignment expressions use `set_index_result`; its input is
`[array, index, value]` and its output is `[value]`. This is distinct from
`set_index`, whose object result lets literal construction append another
element. Intermediate mixed suffixes continue to use ordinary `get_property`
or `get_index` instructions.

## Receivers

Receiver-aware functions use `init_receiver_frame`, `load_this`, and
`return_receiver_locals`. The caller appends one hidden receiver after the
evaluated arguments. Frame initialization leaves the ordinary count and local
slots in their existing positions and keeps the receiver immediately after the
fixed local region. Temporary operands can therefore grow above it without
changing its address.

These instructions are optional rather than a new field in the invariant VM.
Ordinary closures and bytecode remain unchanged. The optional thenable driver
uses these instructions to invoke a guest `then` function with the source
object as its receiver; it schedules chained thenables as separate jobs.

## Strict equality

The optional `strict_equal` and `strict_not_equal` instructions each consume
two values and produce a tagged boolean. Their implementation is statically
composed with the enabled value representations: the identity-only build does
not link number or string storage, while scalar builds compare numbers and
string contents according to JavaScript strict-equality semantics. Collection
SameValueZero remains a distinct operation because its treatment of `NaN`
differs.

## Short-circuit logical operations

`jump_if_falsy_or_pop` implements `&&`; `jump_if_truthy_or_pop` implements
`||`. Each reads the top operand without copying it. When the operand selects
the expression result, the instruction jumps and leaves it in place. Otherwise
it pops that operand and falls through to the right expression. Forward targets
are ordinary relocation entries, so the same representation works inside
nested function bodies without native callbacks or an AST at runtime.

These instructions belong to `logical-operations`, not basic `control-flow`.
Consequently a machine needing loops and `if` but no logical expressions does
not decode them or link their truthiness composition.

Conditional source expressions need no additional instruction. The compiler
emits `to_boolean`, `jump_if_false_boolean`, the consequent, an unconditional
`jump`, and the alternate. Both targets use ordinary relocation records when
the expression is inside an appended function body. Thus a runtime capable of
`if` already has the complete execution vocabulary, while a reduced compiler
can omit the `?:` parser branch independently.

## Numeric targets

`const_f64` belongs to number representation; `add_number`,
`subtract_number`, `multiply_number`, and promoted relational operations
belong to the separate number-operations capability. Numeric equality and
storage can therefore omit all arithmetic decoder arms.

The compiler target is explicit. A JavaScript-number target emits an invariant
i30 opcode only when its result is statically known to fit, and otherwise emits
the promoted operation. A bounded-i30 target emits only the smaller integer
instruction family and reports overflow at execution. This is a build target,
not a language-visible claim that JavaScript integers stop at 30 bits.

Collection-literal expression support is entirely a compiler composition.
Both the reduced numeric loop and the general-expression loop emit the same
`new_array`/`set_index` and `new_object`/`set_property` instructions. Therefore
enabling richer literal source syntax adds no decoder branch or runtime
dispatch, and omitting it can discard parser code without changing bytecode
semantics.

## Untagged template literals

Bare template literals do not require a new instruction. Cooked literal pieces
enter the existing constant pool. Each substitution uses the ordinary
expression compiler, and the pieces are combined with the existing `add`
instruction, whose string coercion supplies template interpolation semantics.
Tagged templates are intentionally not part of this milestone.

The Rust engine currently keeps `ConcatenateStrings` removable and strict: it
accepts only two existing strings. This gives statically proven concatenation
a small implementation without pretending to provide the general coercion
required by template substitutions.

## Async functions and await

An async function body reuses ordinary frame, local, capture, and return
instructions. The optional `async_closure` constructor distinguishes its call
boundary from an ordinary closure: a call returns a pending Promise to the
caller while its body runs in an independent guest context. Builds omitting
`async-functions` neither decode that constructor nor link its closure and
invocation storage.

Declarations, anonymous function expressions, and arrows emit that same
constructor. A named recursive async expression emits
`recursive_async_closure`, whose separate composition crate adds a private
self cell to async closure storage. Builds needing async functions but not
recursive self identity do not decode or link that constructor.

`await` suspends after evaluating one operand. It retains the function's
arguments, locals, operand stack, program counter, exception state, and live
captured-variable references, then resumes with either a fulfilled value or a
thrown rejection.

The runtime stores suspended contexts in GC-visible engine objects and
schedules their continuation through the same bounded FIFO Promise job queue
used by `then`. A caller-supplied async frame array tracks only currently
running nested bodies; once a body reaches `await`, its heap continuation and
Promise reaction replace that scheduler frame. This preserves ordinary
bytecode on either side of an await while making suspension explicit.

The saved context contains the active stack range, frame and handler depths,
and program counter. The scheduler frame separately roots the caller context
and outer Promise. Captured mutable variables remain traced environment cells,
so compaction can relocate the entire graph without exposing raw offsets.

MicroESNext executes a resumed function on its ordinary compact VM stack. It
does not leave every async invocation permanently resident there: while the
function is suspended, its snapshot is an ordinary GC-visible value graph.
Fulfillment restores the awaited operand and continues after `await`;
rejection restores the same frame and enters its existing exception machinery
as though the await expression had thrown.

`try` records a catch target together with the current operand, call-frame, and
outer-handler depths. `end_try` removes that record on normal completion while
preserving the expression result. `throw`, including the abrupt completion
created by a rejected `await`, truncates the guest stack to the nearest record
and resumes at its catch target. None of these operations uses native Rust or
WebAssembly stack unwinding.

The bytecode format version is `2`. Version `1` readers cannot safely infer the
new function metadata or opcode numbering and must reject these artifacts.

Whenever the instruction table changes, tests must cover source execution,
bytecode compilation/loading, stack-size analysis, dumping, relocation, and
the 64-to-32-bit conversion path. An opcode working only in the interpreter is
not considered implemented.

# Rust engine invariants

MicroESNext is not an ordinary Rust object graph wrapped around a bytecode
loop. Its guest machine is a relocatable address space with explicit bounds.
The following rules preserve the properties for which MicroQuickJS is useful.

- Every guest `Value` and heap reference is exactly four bytes on Wasm32 and
  native targets.
- Runtime crates are `no_std`, receive their memory from the caller, and do not
  require libc or a global allocator. Compiler tooling may use `alloc` in a
  separate crate.
- Capacity is not permanently fixed. A caller can move a machine into a larger
  word slice. Heap offsets remain unchanged and the stack is copied against the
  new upper boundary. A Wasm controller can grow linear memory and rebind the
  same offset-based machine state.
- Durable relationships use word offsets. A Rust reference into the arena may
  not survive a call that can allocate or collect.
- The guest heap grows upward and its operand/frame stack grows downward in one
  fixed-capacity buffer.
- Guest calls, parsing, tracing, and suspension must not recurse on the native
  stack.
- Guest allocations do not become individual `Box`, `Vec`, `String`, `Rc`, or
  host allocator entries.
- Collection traces and compacts the arena. Debug tests must relocate live
  graphs frequently enough to expose stale offsets.
- Bytecode and immutable built-ins may be shared outside the mutable arena.
- Capabilities are independent Cargo features within a small set of coherent
  crates linked statically. The base opcode loop does not use trait objects,
  dynamic registries, or callbacks for omitted features.
- Capability bytecodes are feature-gated at decoding as well as execution.
  Bytes assigned to an omitted capability are invalid rather than accepted by
  a larger universal enum and rejected later by the VM wrapper.
- The execution crate's `core` module reads raw bytes and depends only on the
  invariant `microesnext-bytecode::core` vocabulary. It returns any non-core
  byte to the feature-gated typed decoder in `microesnext-vm`; the raw core is
  deliberately not an independent validator for extension opcodes.
- An awaited computation is a heap-resident VM frame. Rust `async fn` and its
  compiler-generated future are host integration options, not its guest
  representation.
- The optional execution `suspension` feature owns conversion between a live
  VM stack and a rooted continuation. The arena supplies generic stack-snapshot
  storage, but the execution `core` module contains no suspend, resume, or restore
  algorithm. Builds without `async` do not expose those machine operations.
- An async JavaScript call cannot suspend its ordinary caller at the first
  `await`. The optional execution `async-functions` layer therefore packages
  the closure and evaluated arguments, snapshots the caller, and starts the
  body in an independent guest context over the same arena. The scheduler can
  restore the caller with the outer promise while the body continuation enters
  that promise's reaction path. A bounded caller-owned frame array permits
  nested async entry without a native recursive call or hidden allocation.
- Guest exception handlers are explicit records in the guest stack. The
  optional execution `exceptions` module owns the handler-chain pointer and
  stack operations; `microesnext-vm` composes it only behind the `exceptions`
  feature, and the invariant opcode core has no exception state. A throw
  restores the recorded operand and call-frame depths without unwinding the
  native Rust stack. Suspension snapshots the active handler depth, so a
  rejected `await` follows exactly the same handler chain as a synchronous
  throw.
- Wasm exception references are an optional foreign-call optimization, not the
  representation of a JavaScript exception. A baseline artifact must remain
  usable by engines that cannot validate `exnref`; a separately selected build
  may catch and rethrow opaque host or foreign-Wasm exceptions unchanged.
- Scheduler and host references use O(1), generation-checked root slots. Raw
  moving heap offsets are not exposed as durable asynchronous handles.
- Native Promise adoption is an optional composition over compact Promise
  storage. It registers an identity reaction in the caller-owned queue rather
  than recursively following a chain on the Rust or WebAssembly stack. Its
  compact error dependency turns self-resolution into a guest TypeError
  rejection rather than an engine-control error.
- Receiver-aware invocation is an optional frame composition. It reuses the
  existing argument entry path with one hidden value after fixed locals; the
  invariant `Core`, ordinary frames, and builds omitting `receivers` are
  unchanged. Object thenable assimilation uses this boundary rather than a
  host callback or proxy.
- Promise resolving functions are compact callable records rather than guest
  closures. A resolve/reject pair shares one traced `alreadyResolved` cell and
  yields a payload-free VM outcome; optional machine state carries the call to
  its controller without changing the invariant core or the public outcome
  layout under Cargo feature unification.
- Thenable resolution is split into synchronous inspection and rooted jobs.
  Guest `then` code is never invoked inline while resolving a value. If its
  resolving function receives another thenable, execution returns a new job to
  the controller, preserving ECMAScript deferral without native recursion.
- Async completion is generic over a statically dispatched resolution policy.
  Its ordinary public entry points monomorphize with native Promise resolution;
  The scheduler `async-thenables` feature supplies a separate policy holding a
  bounded,
  caller-owned thenable-job queue. The same policy can park an `await` on an
  intermediate Promise before resolving an object operand, while native
  Promises and primitives retain the direct path. This adds no trait object,
  callback, or branch to a build that omits the composition.
- Packed byte strings, atom tables, objects, and closures remain arena blocks;
  they do not become Rust allocations merely because their implementations are
  split across crates.
- Small integers remain immediate i30 values in the invariant core. Optional
  IEEE-754 numbers use opaque two-word payloads from the values `numbers` feature, so
  arbitrary floating-point bits are never traced as guest references. Builds
  without `numbers` omit the arena block kind, typed opcodes, and implementation.
- Unary integer and JavaScript Number negation are separate capability modules
  from binary arithmetic. The promoted path preserves negative zero, while a
  build needing only multiplication or comparison retains neither negation
  implementation nor either negation opcode.
- Division and remainder are separate from each other and from ordinary
  arithmetic. This is not only taxonomy: linked Wasm showed that floating `%`
  retains a substantially larger helper than `/`. A division-only machine has
  no remainder opcode, implementation, or dispatch branch.
- Primitive Number coercion is a further capability boundary. Its typed result
  lets promoted negation consume a coercion result once, while its pre-existing
  i30 branch remains ahead of coercion. Unary plus materializes a boxed value
  only for NaN. String parsing and object coercion are deliberately absent
  rather than host-defined.
- String Number coercion is layered above that primitive module. It borrows the
  packed arena payload directly, validates the whole grammar, and allocates
  only the resulting boxed number when an immediate i30 cannot represent it.
  Power-of-two integer parsing keeps explicit guard/sticky bits; no temporary
  guest string participates in those paths.
- Decimal conversion is a separate leaf module shared by compiler literals and
  string coercion. Its exact fast path and bounded correctly-rounded fallback
  contain no allocator or runtime policy. Static Cargo composition removes the
  code and its call sites when neither consumer is selected.
- `typeof` is another leaf policy rather than a method on the VM. Its base
  build recognizes immediates, strings, ordinary objects, and closures;
  optional arena kinds extend the same direct match through Cargo feature
  unification. It allocates an ordinary string and requires no atom table.
- Ordinary strings, atom interning, and objects form three boundaries. A string
  value is not automatically retained or interned. Atoms add a rooted table;
  objects compose atoms for source-level property names. A string-only machine
  links neither atom nor property-table operations.
- Symbols are individually allocated identities whose optional descriptions do
  not participate in equality. Object and collection tables already compare
  compact `Value` identities, so symbols compose as keys without either table
  depending on the values `symbols` module. The arena symbol kind is feature-gated.
- Iterator positions are guest-arena state rather than native Rust cursors.
  The source-agnostic objects `iterators` module retains the iterable and
  current index across collection. Array and Map/Set traversal live in separate
  adapter modules, preserving both dependency and code-size isolation.
- SameValueZero is capability-aware without runtime registration. A standalone
  collection build compares compact identities directly. Cargo weak-feature
  forwarding statically adds string-content and boxed-number equality only
  when collections are composed with those scalar features.

The first Rust vertical slice deliberately supports only i30 constants,
addition, `await`, and return. It proves that the interpreter can suspend after
